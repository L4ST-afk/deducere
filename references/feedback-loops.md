# 反馈回路搭建目录（辨征问展开卷）

> 配合 `对鸟Deducere` 使用。正文只保留「先有一条能对**这个** bug 变红的命令」硬闸；本卷给各接缝的构造顺序、收紧方向与降级路径。

## 目录

§一 十种接缝（按顺序试）｜§二 收紧回路｜§三 非确定 bug｜§四 真建不出回路｜§五 完成判据｜§六 性能回归复测

## 一、十种接缝（按顺序试）

在能触到 bug 的最浅接缝建回路，从可自动复现到要人介入逐级下沉：

1. **失败测试**：单元／集成／端到端，哪层够得着 bug 就用哪层。
2. **HTTP 脚本**：对运行中的开发服务发请求，比对响应。
3. **CLI 调用**：喂固定夹具输入，stdout 对已知良好快照 diff。
4. **无头浏览器脚本**：驱动 UI，断言 DOM／console／网络。
5. **回放已抓 trace**：把真实请求／载荷／事件日志存盘，隔离回放进代码路径。
6. **一次性 harness**：起最小子集（单服务、mock 依赖），一次函数调用走到 bug 路径。
7. **属性／fuzz 回路**：「有时输出错」类，跑批量随机输入找失败模式。
8. **二分 harness**：bug 出现在两个已知状态之间，自动化「起 X 状态、检查、重复」，可接 `git bisect run`。
9. **差分回路**：同一输入过旧版 vs 新版（或两套配置），diff 输出。
10. **人工介入脚本**：最后手段。必须人点时，用 `scripts/human-loop.template.sh` 把人也结构化进回路；采集到的输出再喂回给 agent 的四问三账。

**抽象交互层接缝**：UI／移动端／桌面交互类 bug，先判断能否在更底层接缝复现（组件调用、事件回放、状态快照）；只有底层接缝够不着时才上交互层脚本。⛔ 不把某一宿主的具体浏览器、视口尺寸、端口写进通用流程——那是当次任务的耦合。

UI／显示类回路按症状选证据面（接缝深度见 J16），三面各管一件事，⛔ 互相代结：
- **真值层**：API／状态文件中的对象、状态、数值与时间片。
- **结构层**：DOM、计算样式、事件命中与真实调用参数。
- **表现层**：像素、实际交互、动画帧率与外部效果。
计算样式绿不替像素验收，截图不替鼠标／键盘走查，mock 的调用通过不替真实浏览器、服务或投递效果。

**报错类型 → 首选接缝**（只给首选入口，根因另判）：

- 语法／类型错 → 失败测试。
- 连接拒绝 → HTTP 脚本／CLI 调用。
- 超时／等待类 → 条件等待＋计时回路。
- 断言失败 → 差分回路。
- 无报错但结果错 → 属性／fuzz 回路。

**性能与时序接缝**：

- 性能回归：用既有基准脚本，修复前后跑**同一命令**，取 rc＋耗时对比；候选红判据挂 T11，未转正前不得写成正式 J 条目。四条测量纪律（同条件基线／单变量定位／越波动才算赢／记账防重）展开见 [performance-measurement.md](performance-measurement.md)；量具与优化模式由独立 `performance-optimization` 提供，本件不搬通用预算，也不写未经实测的毫秒／百分比数字。
- 时序／并发：加压、并行、收窄时序窗、注入等待（接 §三）；竞态类用固定随机种子＋受控并发复现，⛔ 靠加大超时掩盖。

## 二、收紧回路

有了**一条**回路后，把它当产品收紧：

- **更快**：缓存 setup、跳过无关初始化、收窄测试范围。
- **信号更锐**：断言具体症状，不是「没崩」。
- **更确定**：钉时间、固定随机种子、隔离文件系统、冻结网络。

**服务实例新鲜度**：改码后的复测先核对跑的是哪一份。记录旧 PID／启动时间／版本或内容指纹；停止后先确认旧进程与监听已退，再启动新实例；复测命令须断言新指纹，不能只探「端口还能连」。有构建指纹的服务，把指纹断言接进 `verify_red_green.py --match`，防止旧实例抢先复用端口。

一条 30 秒的 flaky 回路不比没有强多少；2 秒确定性回路才是调试杠杆。

**批量回路先量闸耗时**：一条回路要跑 N 次、每次还带几道重闸时，先量每道闸的秒数（命令＋耗时进过程账）再排批次。单轮总时长超过宿主的前台等待上限，进程会被挪到后台、甚至中途被停，留下「写了一半」的现场——这不是环境问题，是回路设计问题。能「写 N 次、闸 1 次」就这么设计，并给收口步一个幂等的续跑入口；同一棵树、同一状态，一道闸在一次运行里⛔ 不跑两遍。（2026-11-28 一次判据集录入链：每条约 195s，五条被超时踢停，验收块停在旧计数。）

## 三、非确定 bug

目标不是干净复现，而是**提高复现率**：连触发 100 次、并行、加压、收窄时序窗、注入等待。50% 复现率可调试；1% 不可调试，先把复现率抬到可调试区间。
- **彻底不可复现时**：只收边界与诊断（触发条件、已排除项、证据级），⛔ 硬修；等采集件到位再开回路。

## 四、真建不出回路

明确停下并说清：列已试过的路径，向用户要 (a) 能复现的环境访问权，(b) 脱敏采集件（HAR／日志转储／core dump／带时间戳录屏），或 (c) 临时加生产侧插桩的许可。⛔ 没有回路就进入假设阶段。

## 五、完成判据（判据见判据表 J1–J4）

本卷不复写判据句：辨征问出口的四种状态（能变红／确定／快／agent 可跑）及其「判违规的样子」在 `判据表.md` J1–J4。本卷只补机制侧两点：

- **「能变红」的定义**：走到真实 bug 代码路径、断言用户的确切症状、修后能转绿；「不报错」不算。
- **机锁用法**：`scripts/verify_red_green.py --expect red --cmd "<命令>" --match "<症状正则>"`——非零退出码且命中症状才算故障锁定；命令竟返回 0，判假复现。

**自造红灯（没有现成红灯命令时）四条**：现成红灯由用户／CI 给出，症状是别人断言过的；自造的红灯，锁错的风险全在自己身上。2026-11-28 一次判据集录入链三条红重锁三次才对——每次都是机锁拦下的，不是症状变了：

1. **先原样跑、读失败行，再上锁**：`--match` 写的必须是那条命令实际打出的失败行，⛔ 不写「我估计它会报的」。机锁报「症状不匹配」时先读它给出的实际末行，⛔ 改 `--match` 去迁就输出（那是凑红，与凑绿同罪）。
2. **探针输入先过无关的闸**：名字要唯一、编号与载体首行一致、路径要存在。否则红会被别的闸截胡——看起来「红了」，红的是另一件事（J2）。
3. **包装器映射写对、两股流都收**：「见症状 ⇒ 非零」；很多闸把判词打到 stderr，只收 stdout 会把红读成绿。
4. **「缺入口」类缺陷的红灯不是「命令不认识这个参数」**，是没有该入口时用户撞到的那个失败；现场造不出来就在影子副本里造（能撤、不碰正本）。

## 六、性能回归的复测与撤码（候选口径挂 T11）

性能回路的红不是「这次慢了」，而是同一症状指标在同一接缝上可重复地越界。基线与复测钉住命令、输入、机器／负载、缓存、样本数；冷缓存对冷缓存，热对热。每轮多次取样，报中位数与轮间波动，⛔ 拿一次最好值当证据。

- 一次只改一个性能变量；必须同批落地，先分别量，再合并量。
- 指标未越过噪声带＝证据不足；撤回本次为性能新增的复杂度。更差或功能测试红同样撤回，⛔ 用性能数字抵功能债。
- 保留和撤回都进过程账：问题／机制／证据（基线→结果、波动、命令与 rc）／判据（T11，未转正）。⛔ 另开 `PERF.md` 当第二本账。
- 量测工具、Web／后端／数据库优化模式去独立 `performance-optimization` 查；回到本件时只带命令、样本、rc、数字与根因链。

当日 profile 绿只结过程账；真实使用是否不再掉帧／变慢，仍等隔期或换宿主复验。
